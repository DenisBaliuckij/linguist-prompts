# Prompts: Spanish · lemmatization

## 1. Построение испанской морфологической онтологии

**Назначение:** создать проверяемую языково-специфичную онтологию, из которой можно извлечь правила и лексические исключения для лемматизации.

```text
Ты - лингвист-испанист и инженер лингвистических данных. Создай JSON-файл
`OntoSpanish.json` для современного письменного испанского языка (ISO 639-3:
spa). Работай только с приложенными источниками. Не дополняй их знаниями из
памяти и не выдумывай правила, примеры или ссылки.

Вход A: общая онтология грамматики человеческого языка (GOLD OntoLing).
Вход B: приложенные академические грамматики, словари и описания испанского.

Задача: сохрани совместимые с Input A разделы, но заполни их только фактами
из Input B. Не создавай сокращённую демонстрационную онтологию: перенеси все
релевантные для лемматизации факты и парадигмы из Input B. Главная цель файла
- поддержать рабочий rule-based лемматизатор с максимально полным покрытием
переданных данных, поэтому в разделе Morphology обязательно отрази:

- части речи и их словарные формы;
- парадигмы существительных и прилагательных: число, род, орфографические
  чередования и случаи, в которых ударение невозможно восстановить правилом;
- глагольные классы -ar, -er, -ir; конечные формы, герундий, причастие,
  времена и наклонения;
- возвратные клитики, апокопу и многословные формы, если они описаны в
  источниках;
- нерегулярные парадигмы как таблицы "словоформа -> лемма" или как ссылки на
  лексикон;
- каждое ограничение, при котором поверхностная форма неоднозначна и одного
  правила недостаточно.

Для каждого правила запиши: входной шаблон, выходную лемму или операцию,
условия применения, минимум один пример, ссылку на источник и статус
`rule`, `lexicon_required` либо `ambiguous`. Не подменяй неизвестные данные
правдоподобным заполнением: пропусти их и добавь запись в `gaps` с причиной.

В meta укажи: название, версию, язык, ISO-код, все реально использованные
источники, дату и область охвата. Сначала проверь, что JSON валиден, все
примеры соответствуют правилу, а каждый факт имеет источник.

Верни только валидный JSON в UTF-8 без Markdown и комментариев.
```

## 2. Подготовка gold use-cases

**Назначение:** получить независимый набор эталонных пар «словоформа -> лемма» для проверки лемматизатора.

```text
Ты - куратор лингвистических данных. Подготовь два непересекающихся набора
gold use-cases для лемматизации современного письменного испанского:
`development` и `holdout`.

Разрешены только заранее размеченные источники, где лемма дана источником, а
не предсказана тобой. Предпочти UD Spanish AnCora в формате CoNLL-U, потому
что у него есть FORM, LEMMA, UPOS и FEATS. Не используй UD Spanish GSD как
единственный gold-источник: его README указывает, что леммы получены
автоматически. Если используешь иной источник, явно укажи происхождение
лемм и лицензию.

Алгоритм:
1. Зафиксируй источник: название, URL, версию или commit, лицензию,
   утверждение о типе разметки.
2. Извлеки только нетривиальные случаи, где FORM не равна LEMMA после
   Unicode case folding. Сохрани sentence_id и token_id, чтобы каждую пару
   можно было проверить в первоисточнике.
3. Раздели данные по предложениям, а не по отдельным токенам: предложения не
   должны попадать в оба набора.
4. Сделай `development` из 200 или более случаев для написания правил и
   `holdout` из 200 или более случаев, который нельзя показывать при создании
   онтологии, словаря или кода.
5. В каждом наборе посчитай случаи по UPOS и морфологическим признакам.
   Если представленность неравномерна, не скрывай это.

Верни два валидных UTF-8 YAML-файла. В каждом используй структуру:

language:
  name: Spanish
  iso639_3: spa
source:
  name: ...
  url: ...
  version: ...
  license: ...
  annotation_type: ...
split: development | holdout
selection: ...
cases:
  - sentence_id: ...
    token_id: ...
    form: ...
    lemma: ...
    upos: ...
    features: ...

Не исправляй, не нормализуй и не переписывай gold-леммы. Если встретил
подозрительную разметку, сохрани её как есть и добавь поле `annotation_note`.
После создания проверь: YAML парсится, все случаи нетривиальны, ID уникальны,
а предложения между наборами не пересекаются.
```

## 3. Создание rule-based лемматизатора

**Назначение:** сгенерировать локальный Python-лемматизатор по онтологии и development-набору, не используя holdout-набор.

```text
Ты - Python-инженер и испанист. Создай один файл
`spanish_lemmatizer.py` с классом `SpanishLemmatizer`. Используй только:

- `OntoSpanish.json`;
- `spanish-development.yaml`;
- стандартную библиотеку Python 3.11+.

Никогда не читай `spanish-holdout.yaml`: он зарезервирован только для
независимой оценки.

Обязательный API:

class SpanishLemmatizer:
    def __init__(self, ontology_path="OntoSpanish.json") -> None: ...
    def lemmatize(self, form: str, upos: str, features: str = "_") -> dict[str, str]: ...
    def lemmatize_sentence(self, tokens: list[dict]) -> list[dict]: ...

Требования:
1. Загрузи правила, статусы правил и лексические исключения из онтологии, а
   не создавай независимый несовместимый список правил в коде. Построй
   используемый лексикон из всех лексических исключений и парадигм,
   представленных в онтологии и development-наборе, а не из короткого
   демонстрационного списка.
2. Верни лемму в нижнем регистре; сравнение может быть accent-insensitive,
   но не теряй диакритики в лемме, если они известны из лексикона или правила.
3. Сначала примени точные словарные исключения, затем правила с наиболее
   специфичными условиями, затем общие правила.
4. Применяй правила числа и рода только при соответствующих UD-признаках.
   Не снимай суффиксы у форм без достаточных оснований.
5. Для неоднозначных окончаний -er/-ir, апокопы и восстановление акцентов
   используй лексические данные. Если данных нет, верни форму без изменений
   в поле `lemma`, поставь `confidence="ambiguous"` и объясни причину в поле
   `reason`; не выдумывай лемму.
6. Поддержи как минимум NOUN, ADJ, VERB и AUX. В `lemmatize_sentence`
   сохрани исходный токен, лемму, применённое правило и уверенность
   `exact`, `rule`, `lexicon` или `ambiguous`.
7. Добавь `evaluate(cases_path)` с exact-match accuracy и разбиением по UPOS;
   функция должна записывать CSV с form, expected, actual, UPOS, статусом и
   причиной ошибки.
8. В module docstring перечисли известные ограничения. Не заявляй о полной
   лемматизации испанского без полного словаря и парадигм.

Каждый результат `lemmatize` должен иметь ровно поля `lemma`, `rule`,
`confidence` и `reason`. Например:

{"lemma": "entrar", "rule": "preterite_ar", "confidence": "rule", "reason": ""}

или, если правило неприменимо без лексикона:

{"lemma": "vivió", "rule": "", "confidence": "ambiguous", "reason": "cannot distinguish -er from -ir"}

Перед выводом выполни development-набор и сообщи число ошибок по категориям.
Верни только содержимое Python-файла без Markdown.
```

## 4. Независимая оценка лемматизатора

**Назначение:** измерить качество готового лемматизатора на скрытом наборе и получить диагностический отчёт.

```text
Ты - инженер по оценке NLP. У тебя есть:

- `spanish_lemmatizer.py`;
- `OntoSpanish.json`;
- `spanish-holdout.yaml`.

Нельзя менять лемматизатор, онтологию, словарь или holdout-набор после того,
как увидены результаты. Запусти для каждого case:

result = SpanishLemmatizer().lemmatize(form, upos, features)
actual = result["lemma"]
passed = actual == lemma

Создай два файла:

1. `spanish-evaluation-results.csv` со всеми случаями без исключения:
   sentence_id, token_id, form, expected, actual, upos, features, status,
   rule, confidence, reason.
2. `spanish-evaluation-report.md` со следующими разделами:
   - источник и версия holdout-набора;
   - число тестов, верных ответов, ошибок и exact-match accuracy;
   - accuracy и количество случаев по UPOS;
   - accuracy по типам форм, если признаки это позволяют;
   - не менее 20 первых ошибок с ID, формой, ожидаемой и полученной леммой;
   - группировка ошибок: отсутствующее исключение, неверный класс глагола,
     акцент, род/число, апокопа, неоднозначность, ошибка разметки, прочее;
   - ограничения теста и конкретные следующие улучшения.

Не удаляй неудачные случаи, не исправляй gold-разметку и не округляй
результаты так, чтобы скрыть ошибки. Если код не запускается, это тоже
результат: укажи traceback и поставь accuracy `not computed`.
```
